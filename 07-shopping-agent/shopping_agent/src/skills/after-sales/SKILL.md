# 售后处理流程

这个文件是给模型看的**流程知识**，不是代码。规则会变，写法也会变，
放在 markdown 里改一行就生效，不用改代码、不用重新部署。

工具负责把事实查准（签收时间、订单状态、类目、引用的条款），
判定按下面的流程走。两者不要混。

## 一、先取事实，再下结论

回答任何售后问题之前，先调 `check_return` 拿到：

- 订单状态（待发货 / 已发货 / 已签收 / 已取消 / 售后中）
- 签收时间与距今多少天
- 商品类目与子类
- 检索到的相关条款原文

**不要凭印象回答时效、运费、比例这类问题。** 这些数字每个平台都不一样，
而且会改。查不到就说没查到。

## 二、按状态分流

| 订单状态 | 能做什么 | 注意 |
|---|---|---|
| 待发货 | 可以取消订单、改收货地址 | 取消后优惠券是否退还要看券的规则 |
| 已发货 | 可申请退货，但要等签收后才能寄回 | 途中拦截成功率取决于物流进度，不要承诺一定拦住 |
| 已签收 | 按下面的时效判定 | 时效从**签收次日**起算，不是从下单起算 |
| 已取消 | 通常已退款，只需说明退款时效 | 不要重复承诺退款 |
| 售后中 | 已有工单在处理 | 先查工单，不要重复建 |

## 三、时效判定

1. **七天无理由**：签收次日起七日内。超一天就是超一天，不要含糊说「差不多可以」。
   数码类（耳机、键盘、显示器）要求包装完整、配件齐全。
2. **质量问题**：不受七天限制，按保修期走。保修期以商品详情里的
   `warranty_months` 为准，从签收日算。
3. **超过七天的无理由**：明确告诉用户不符合，同时给出还能走的路径
   （质量问题走保修、或者申请人工介入）。

## 四、运费判定

- 质量问题、发错货、运输损坏 → 平台承担
- 七天无理由 → 用户承担，除非商品带运费险
- 换货 → 首次换货运费平台承担，二次换货看责任方

## 五、几个不要做的事

- **不要承诺具体退款到账时间。** 规则里写的是「按原支付渠道退回」，
  到账时间由支付渠道决定，说「3 到 5 个工作日」是在编。
- **不要承诺拦截一定成功。** 物流拦截有成功率，取决于包裹到了哪一环。
- **不要把邻近的规则当答案。** 用户问「满减和优惠券能不能一起用」，
  检索可能返回「发票怎么开」。答不上就说没查到，或者建工单问人工。
- **不要在超期时给用户留希望。** 明确说不行，再说还有什么路可走。

## 六、什么时候建工单

以下情况直接建 `create_ticket`，不要反复查规则：

- 用户明确要求人工介入或投诉
- 规则里确实没有覆盖（比如促销叠加的具体口径）
- 涉及金额争议、商品质量责任划分
- 同一个问题问了两轮还没解决

工单要写清楚：订单号 + 用户描述的问题原话。不要自己加工成结论。
